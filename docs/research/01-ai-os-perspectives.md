# AI向けOS 最適化観点の調査

- 調査日: 2026-11-08
- 対象: Windows / macOS / Linux / Android / iOS（＋参考として HarmonyOS など）
- 目的: 既存OSが「AIに最適化されていない」箇所を洗い出し、OtaS の設計論点を明らかにする

> 注記: 2026年の商用OSの動向（Windows Build 2026、WWDC 2026 など）は二次情報（業界メディア）に基づくものが多い。未確認の情報には「（報道ベース）」と付記した。実装判断の前に一次情報を確認すること。

---

## 0. 要約

1. **既存OSの前提は「操作者＝人間」「プログラム＝信頼できる決定的なコード」**。AIエージェントはこの両方に当てはまらない。エージェントは人間の代理として高速に動き、確率的に誤る。さらに、読んだデータに騙されることがある（プロンプトインジェクション）。
2. ずれは主に **インターフェース・権限・可逆性・実行モデル・資源・監査** の6領域に出ている。商用OSはどれも「後付け」で対応中（Windows の Agent Workspace と MCP、Apple の App Intents、Android の AppFunctions）。ただし各社独自の仕組みで、OS をまたいだ標準はない。
3. 設計の中心に置く候補として、Unix の「プロセス」と「ファイル」に相当する2つの抽象を提案する。
   - **Task**: 委任元・権限・作業領域・予算・監査ログを持つ作業単位。隔離されていて、取り消せて、記録が残る。
   - **Action**: アプリやサービスが公開する、型付きの機能。副作用の種類（読み取りのみ／取り消し可能／取り消し不可／外部送信）を宣言する。
   - これに **来歴ラベル付きデータ** を加えた3つで、権限・承認・undo・監査の大半の観点を統一的に扱える。
4. OSS として中身を変えられるのは事実上 Linux（と AOSP）だけ。**Linux の上にエージェント実行基盤を作るのが現実的**で、新しいカーネルは不要と考える。必要な隔離や監視の部品（Landlock / seccomp / eBPF / LSM）はすでに揃っている。

## 1. 前提：「AI用OS」の3つの意味

| レイヤー | 意味 | 主な論点 | OSSでの勝ち筋 |
|---|---|---|---|
| **A. AIを動かすOS**（推論基盤） | LLMの推論・学習を効率よく実行する | GPU/NPUのスケジューリング、メモリ、モデルの共有 | 中。ハードウェアベンダーとドライバに強く依存。ユーザーランドでは vLLM や llama.cpp などが既に強い |
| **B. AIが使うOS**（エージェント実行基盤） | エージェントが安全・確実にOSを操作する | 権限、隔離、undo、監査、型付きのインターフェース | **高い**。オープンな標準が存在せず、商用OSは独自の仕組みに分かれている |
| **C. AIで使うOS**（人間向けUX） | 人間が自然言語でOSを使う | 意図ベースのUI、承認UX、人間とAIの協調 | 中。B の上に乗るもの |

**本調査では B を中心に、A と C も含めて観点を洗い出す。**

## 2. 根本的なずれ：既存OSの前提と、エージェントの実態

| 観点 | 既存OSの前提 | AIエージェントの実態 | 必要な新しい抽象 |
|---|---|---|---|
| 主体 | 操作者は人間（uid）。操作は遅く、本人が責任を負う | 人間の代理として高速に大量の操作をする。複数のエージェントが同時に動く | 「誰の代理で、どのタスクとして」動いているかを表すアイデンティティ |
| 権限 | アンビエント権限（ユーザーが持つ全権限をそのまま継承） | タスクに必要な権限はごく一部。しかも騙されうる | タスク単位・期限付き・目的限定のケイパビリティ |
| データ | ただのバイト列。信頼度の区別がない | 読んだデータが命令として働きうる | 来歴と信頼度のラベルが付いたデータと、情報フロー制御 |
| インターフェース | 人間向けのGUI（ピクセル）と人間向けのテキスト | 画面解析は遅く、高コストで、壊れやすい | 型付きで発見可能なアクション、意味構造を持ったUI、構造化された入出力 |
| 副作用 | 即時に反映され、取り消せないのが基本 | 確率的に動くため、人間より誤操作が多い | ステージング、プレビュー、スナップショット、取り消し |
| 実行単位 | 短命なプロセスと端末セッション | 数時間〜数日かかるタスク。人間の返答待ちで中断する | 永続化・再開ができるタスク |
| 資源 | CPU時間、RAM、ディスク | GPU/NPU、モデルの重み、KVキャッシュ、コンテキスト長、トークン費用 | 計算資源・コンテキスト・予算をOSの資源として管理する仕組み |
| 記録 | システムコールやイベント単位のログ | 「なぜその操作をしたのか」が重要 | ユーザーの指示や計画と結びついた監査ログと、リプレイ |
| 人間の役割 | 操作者 | 監督者・承認者 | リスクに応じた承認、介入、操作の引き継ぎ |

## 3. 観点一覧（5カテゴリ・22観点）

### A. 操作インターフェース

#### A1. 機能の発見と型付き呼び出し
- **問題**: アプリが「何ができるか」を機械可読な形で公開する、OS横断の標準がない。そのためエージェントはGUIを手探りするか、アプリごとのAPIを個別に実装するしかない。
- **現状**:
  - Windows: OS組み込みのMCP（On-device Agent Registry、プレビュー）、App Actions
  - macOS / iOS: App Intents。WWDC 2026 で Siri の中核になったと報じられている。Xcode 27 は MCP / ACP に対応（報道ベース）。OS全体でのMCP対応は未確認
  - Android: AppFunctions（Android 16〜）。Google 自身が「デバイス上のMCPに相当する」と説明している
  - HarmonyOS 6: HMAF（Agent Framework Kit / Intents Kit）
  - Linux: D-Bus はあるが、スキーマ・意味の記述・エージェント向けの権限がない
- **方向性**: OSレベルの**ツールレジストリ**を設ける。アプリやサービスが型付きのアクション（入出力スキーマ、副作用の種類、取り消し可否、必要な権限）を宣言し、OSが発見・認可・監査を仲介する。プロトコルはMCP互換にする。
- **設計上の要点**: **副作用メタデータを必須にする**。これがあれば、権限（B2）・承認（B7）・undo（B5）の判定をすべて自動化できる。

#### A2. GUIの機械可読化
- **問題**: スクリーンショットと座標クリックによる操作は、遅く、高コストで、壊れやすい。アクセシビリティツリーは不完全で、OSごとにAPIが違い、権限の粒度も粗い。
- **現状**:
  - Windows: UIA。レガシーなWin32アプリでは情報が欠ける
  - macOS: AX API。TCCによる許可がエージェント単位ではなく、ホストアプリ（Terminal など）単位になる
  - Linux: AT-SPI はアプリによって品質がまちまち。さらに **Wayland は設計上、他のウィンドウの画面取得と入力の合成を禁止している**。回避するには xdg-desktop-portal や libei を使い、コンポジタごとの対応が必要になる。Ubuntu 26.04 LTS では Xorg セッションへのフォールバックがなくなった
  - Android: AccessibilityService は強力だが、マルウェアに悪用されたため制限が強まっている。別途 Gemini 向けの UIオートメーションフレームワーク（限定プレビュー）がある
  - iOS: サードパーティのアプリが他のアプリを操作する手段はない
- **方向性**: コンポジタやUIツールキットの層で、意味構造を持ったUIツリーを標準で出力する。エージェント専用の入力チャネルを設け、人間の入力と分離して、誰の操作かを記録する。エージェント専用の仮想デスクトップも用意する（Windows Agent Workspace、UFO² の Picture-in-Picture デスクトップ、kwin-mcp の仮想セッションが先例）。

#### A3. CLI・API・エラーの機械可読化
- **問題**:
  - 出力が人間向けに整形されている
  - ページャー・確認プロンプト・TTY依存の対話でエージェントの処理が止まる
  - 出力がロケールに依存する
  - エラーメッセージが構造化されていない
  - man ページが長すぎる
- **方向性**:
  - 全コマンドに構造化出力（JSON）と非対話モードを用意する
  - エラーを構造化する（原因と対処の候補を含める）
  - `--help` を機械可読なスキーマにする
  - 時刻・ロケール・権限状態などの環境情報を明示的に提供する
  - 先例は PowerShell のオブジェクトパイプラインと nushell。SWE-agent の研究（Agent-Computer Interface）は、インターフェースの設計次第でエージェントの成功率が大きく変わることを示している

### B. 安全性と信頼

#### B1. エージェントのアイデンティティと委任
- **問題**: エージェントはユーザーと同じ uid、または同じアプリの権限で動くため、ログ上で人間の操作と区別できない。サブエージェントへの再委任も表現できない。
- **現状**:
  - Windows: Agent Workspace で、エージェントごとに専用の低権限アカウントを導入した（プレビュー）。「エージェントの操作はユーザーの操作と区別できる」ことを設計原則にしている
  - 他のOS: こうした概念がない。macOS ではエージェントがホストアプリ（Terminal など）のTCC権限を丸ごと継承する
- **方向性**: 主体を「人間・エージェント・タスク・委任チェーン」の組で表し、すべての操作をそこに帰属させる。

#### B2. 権限モデル
- **問題**: アンビエント権限が前提になっている。モバイルOSの許可はアプリ単位で、一度許可すると永続する。「このタスクの間だけ、このフォルダだけ、読み取りのみ」のような権限を表現できない。
- **方向性**:
  - ケイパビリティベースの権限にする（先例: seL4、Fuchsia、Capsicum、WASI）
  - 権限をタスク単位・期限付き・目的限定にする
  - タスクの計画から必要な権限を自動で導き出し、ユーザーが一括で承認できるようにする
  - Meta の「Agents Rule of Two」をOSのポリシーとして強制する。これは次の3つのうち2つまでしか同時に満たしてはならない、という原則
    - 信頼できない入力を処理する
    - 機密データにアクセスする
    - 状態を変更する、または外部と通信する

#### B3. データの来歴と情報フロー制御（プロンプトインジェクション対策）
- **問題**: エージェントにとって、あらゆるデータは命令になりうる。しかしOSはファイルやネットワークから来たデータの信頼度を区別しない。Simon Willison の言う「致死的三要素」（私的データへのアクセス＋信頼できないコンテンツ＋外部への送信）が、既存OSではそのまま成立してしまう。
- **先例**:
  - CaMeL（Google DeepMind）: 制御フローとデータフローを分離し、ツール呼び出しの時点でケイパビリティのポリシーを適用する。2026年には、コンピュータ操作エージェントにも拡張された
  - FIDES（Microsoft）と Progent: 言語やランタイムの層での先例
  - macOS の quarantine 属性と Windows の Mark of the Web: 来歴ラベルの原始的な先例
- **方向性**:
  - OSが**来歴ラベル**（Web由来、メール由来、ユーザー作成など）をファイルとプロセスに付け、データの流れに沿って伝播させる
  - ラベルに応じたポリシーを適用する。例: 汚染されたコンテキストを持つエージェントには外部送信をさせない
  - エージェントのランタイム（CaMeL型）がOSのラベルを参照できるようにする

#### B4. 隔離・サンドボックス
- **現状**:
  - 各社のエージェントCLIがそれぞれ独自に実装している。macOS では非推奨の Seatbelt API を、Linux では bubblewrap / Landlock / seccomp を使っている
  - 2026年には、Sandlock（root不要で約5msで閉じ込める）、NVIDIA OpenShell、Microsoft Execution Containers（MXC、報道ベース）が登場した
  - クラウドでは Firecracker や gVisor 系のサンドボックスが使われている
- **方向性**:
  - OS標準の**段階的な隔離**（プロセス → コンテナ → microVM）を用意し、宣言的なポリシーで選べるようにする
  - ネットワークの外向き通信をドメイン単位で制御する
  - **認証情報はエージェントに渡さず、OSが代理で注入する**（credential brokering）

#### B5. 可逆性・トランザクション
- **問題**: OSには全体を対象とした undo がないが、エージェントは間違える。
- **現状**: 部品は揃っている（APFS / Btrfs / ZFS のスナップショット、overlayfs、VSS、CRIU）。しかし、タスク単位では統合されていない。Windows のトランザクショナルファイルシステム（TxF）は非推奨になった。
- **方向性**:
  - タスクごとに **CoW（コピーオンライト）のワークスペース**で作業させ、差分をレビューしてからコミットする。システム全体を git のように扱うイメージ
  - dry-run とプレビューを用意する
  - 同じ状態から複数の案を並列に試し、最良のものを採用できるようにする（分岐実行）
  - メール送信や決済のような取り消せない外部への副作用は「コミットポイント」として、明示的な承認を必須にする
  - 先例: Turso AgentFS（SQLiteベース。CoW・スナップショット・監査を備える）

#### B6. 監査・観測性
- **問題**: 既存の監査の仕組み（auditd、ETW、Endpoint Security）はシステムコール単位の記録なので、「なぜその操作をしたか」が分からない。
- **方向性**:
  - ユーザーの指示 → 計画 → ツール呼び出し → システムコール、を結びつけた**監査ログ**を残す
  - 改ざんに強い形式で保存し、リプレイできるようにする
  - ユーザー向けのアクティビティタイムラインを提供する
  - 形式は OpenTelemetry の GenAI セマンティック規約に合わせ、低レイヤーの収集には eBPF を使う

#### B7. 人間の介在（Human-in-the-loop）
- **問題**: 承認ダイアログは「許可／拒否」の二択でアプリ単位。頻繁に出ると承認疲れで形骸化する。また、人間とエージェントが同じマウスやキーボードを奪い合う。
- **方向性**:
  - リスクに応じて承認を段階化する。リスクは、副作用メタデータ・データのラベル・操作対象の掛け合わせで判定する
  - まとめて承認できるようにし、承認したポリシーを学習する
  - 承認を非同期にする（通知やモバイル端末から応答できる）
  - **操作の引き継ぎ**（エージェント⇔人間）を用意する。Android の Gemini UIオートメーションにある live view と手動操作への切り替えが先例

#### B8. サプライチェーン（ツール・スキル・MCPサーバー）
- **教訓（OpenClaw、2026年）**: ローカルで動く個人向けエージェントで、次のような事故が多発した。報告元によって数値の差は大きい。
  - 認証のないゲートウェイがインターネットに大量に公開された
  - スキルマーケットに悪性のスキルが混入した。実行時に外部から中身を取ってくるスキルは、レビューの後で振る舞いを変えられる
  - Webサイトからローカルのインスタンスを攻撃できた（ClawJacked）
  - インフォスティーラー型のマルウェアが、エージェントの設定ファイルとトークンを窃取した
- **方向性**:
  - ツールやスキルに署名と**権限マニフェスト**を必須にする
  - 実行時にコードを取得することを禁止する
  - ローカルのサービスは、デフォルトで認証あり・ローカル限定にする
  - パッケージ単位でサンドボックスに入れる
  - モバイルのアプリストアにおける権限モデルの教訓を応用する

### C. 実行と状態

#### C1. 長時間・永続タスク
- **問題**: プロセスは端末やセッションに紐づき、スリープや再起動で消える。モバイルOSはバックグラウンドでの実行を厳しく制限するため、長時間のタスクが強制終了される。
- **方向性**:
  - 「タスク」をOSの第一級オブジェクトにする。systemd のユニットに、Temporal のような永続実行の仕組みを組み合わせるイメージ
  - チェックポイントと再開、人間の返答待ちによる中断、優先度を扱えるようにする

#### C2. コンテキストとメモリ
- **問題**: コンテキストウィンドウはLLMにとっての「主記憶」だが、OSはそこに関与しない。各アプリが記憶や検索拡張（RAG）を個別に実装していて、プライバシーの管理もばらばら。
- **現状**:
  - Windows: Recall。プライバシーへの批判を受けてオプトイン化された
  - Apple: Siri がユーザーの個人的な文脈を参照できる（App Intents 経由）
  - Spotlight や Windows のセマンティック検索
  - Linux: 標準的な仕組みがない
- **方向性**:
  - アクセス制御付きの**セマンティックインデックス**（ファイル、メール、操作履歴を意味で検索できる索引）をOSのサービスとして提供する
  - エージェントの長期記憶をOSが管理する（MemGPT / Letta の仮想コンテキスト管理をOSに組み込む）
  - LSFS（LLMベースのセマンティックファイルシステム）も先例になる
  - 「いまユーザーが何をしているか」（選択範囲、アクティブなウィンドウ）を、同意を得たうえで取得できるAPIを用意する

#### C3. マルチエージェント協調・通信
- **問題**: 既存のプロセス間通信（パイプ、D-Bus、XPC、Binder、COM）は、プログラム同士のやり取りを前提にしている。エージェント同士の発見・認証・タスクの委譲を扱えない。複数のエージェントが同じファイルを編集すると競合する。
- **方向性**:
  - MCP（エージェント⇔ツール）と A2A（エージェント⇔エージェント）を、OSのプロセス間通信として仲介する
  - 資源をロックやリースで管理し、競合を解決する仕組みを設ける

#### C4. 予算・クォータ
- **問題**: トークン費用やAPIのレート制限は、OSの資源管理の対象外。暴走したエージェントが課金を使い尽くしてしまう。
- **方向性**: cgroups と同じ考え方で、トークン数・金額・API呼び出し回数にタスク単位・エージェント単位の上限を設ける。

### D. AI計算基盤

#### D1. ヘテロジニアス計算のスケジューリング
- **問題**: OSのスケジューラはCPU中心に作られている。GPU や NPU の管理はドライバ任せで、プロセス間の公平性・プリエンプション・QoS が弱い。NPU の API はベンダーごとに分かれている。
- **現状**:
  - Windows: Windows ML / Foundry Local がベンダーごとの実行プロバイダーの違いを吸収している
  - macOS: Core ML / MLX（Neural Engine の詳細は非公開）
  - Linux: カーネルの drivers/accel に Intel NPU や AMD XDNA などのドライバがあるが、ユーザーランドは分断されている。CUDA はプロプライエタリ
  - Android: NNAPI は非推奨になり、LiteRT に移行
- **方向性**: アクセラレータを統一的に扱う資源管理にする。対話的な推論は低遅延を優先し、バックグラウンドのエージェントはスループットを優先する、という QoS クラスを設ける。

#### D2. モデルを共有のシステム資源にする
- **問題**: アプリごとに同じモデルを個別に読み込むため、メモリが重複する。
- **現状**: OSやブラウザが共有モデルを提供し始めている（Apple の Foundation Models framework、Android の AICore / Gemini Nano、Windows AI APIs、Chrome の Built-in AI）。Linux には標準がなく、Ollama などが事実上の標準になっている。
- **方向性**:
  - 重みを mmap で共有する
  - プロンプトの共通部分（プレフィックス）と KVキャッシュをアプリ間で共有する
  - モデルの署名とバージョンを管理する
  - ローカルとクラウドの推論を振り分ける
  - 先例: vLLM の PagedAttention は、OSの仮想記憶の考え方を KVキャッシュの管理に応用している

#### D3. メモリ階層
- **論点**:
  - CPU と GPU がメモリを共有する設計が増えている（Apple Silicon、AMD Strix Halo、NVIDIA GB10）
  - モデルの重みを NVMe → RAM → VRAM の間でページングする
  - HMM（異種メモリ管理）
  - モデルの重みはページキャッシュとの相性が悪い

#### D4. 電力・熱
- **論点**: モバイルや薄型ノートでは、推論の負荷と電池・熱のバランスを取る必要がある。エージェントのバックグラウンド処理は、充電中やアイドル時にまとめて実行する。

#### D5. ローカル推論とクラウド推論の振り分け、プライバシー
- **論点**: データの機密度に応じて推論の場所を選ぶ（先例: Apple Private Cloud Compute）。この判断はB3の来歴ラベルと連動させる。

### E. エコシステムと外部世界

#### E1. アプリ・サービス側の同意と共存
- **教訓（Doubao、2025〜2026年）**: ByteDance の Doubao は、画面を認識して操作するGUIエージェントをOSレベルで搭載したスマートフォンを出した。しかし、WeChat や Alipay、銀行アプリなどのリスク検知に遮断された。第2世代では、MCP / A2A のようなプロトコルベースの連携に移行した。
- **方向性**:
  - エージェントによる操作を、アプリ側が識別・同意・拒否できるようにする（アテステーション）
  - アプリ側にも利益がある公式のチャネル（A1）を用意する
  - 「勝手に画面を読んで操作する」だけでは、エコシステムが成り立たない

#### E2. Webや外部サービスでのエージェントの識別と決済
- **論点**: エージェントの身元を証明する仕組みと、エージェントによる決済が必要になる。
- **先例**:
  - Web Bot Auth（HTTPメッセージ署名でエージェントを識別する仕組み）
  - エージェント決済のプロトコル: AP2、Agentic Commerce Protocol、x402
- **方向性**: OSが署名鍵を管理し、エージェントの身元を代理で証明する。

#### E3. 標準との整合
- **現状**:
  - MCP と AGENTS.md は、Linux Foundation 傘下の Agentic AI Foundation（AAIF）が管理している
  - A2A も Linux Foundation 傘下にある
  - ACP（Agent Client Protocol）はエディタとエージェントをつなぐプロトコル
- **方向性**: **独自のプロトコルは作らず、既存の標準に乗る**。OtaS の独自性は、プロトコルの上にある「OSとしての統合」（権限・undo・監査）で出す。

#### E4. 宣言的・再現可能なシステム構成
- **論点**: エージェントがOS自体を管理するなら、システムの状態がテキストで表現され、差分を取れて、ロールバックできる構成と相性がよい。宣言的に構成する NixOS や、OS をイメージ単位で更新する ostree 系のイミュータブルOSがこれに当たる。
- **先例**: AgntOS（NixOSベース。変更の操作がユーザーの元のプロンプトと一緒に記録される）

## 6. OSSとしての戦略的な示唆

### 差別化ポイント
1. **ベンダーに依存しないエージェント実行基盤**: 商用OSは独自の仕組みを作り、互換性がない（Windows の Agent Registry、App Intents、AppFunctions）。OtaS は MCP / A2A を土台に、権限・undo・監査まで含めた「オープンなリファレンス実装」になれる。
2. **Task / Action / 来歴ラベル付きデータ** の3つの抽象で、B1〜B8 と C1・C4 を一貫して設計する。後付けの商用OSには難しい。
3. **既定で安全**: OpenClaw の教訓を設計原則にする（デフォルトで認証あり・ローカル限定、権限マニフェスト、署名）。

### 実装アプローチの比較
| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| ① ポータブルなエージェント実行基盤 | 既存OSの上で動くデーモン群。ツールレジストリ、権限ブローカー、サンドボックス、CoWワークスペース、監査ログを担う | 早く使ってもらえる。採用の障壁が低い | 各OSの制約（Wayland、TCC など）を越えられない |
| ② Linuxベースのリファレンスディストロ | ①を中核に、イミュータブル／宣言的な Linux、カーネル機能（LSM / eBPF / Landlock）、エージェント対応のコンポジタを統合する | OSのレベルで一貫した設計を実証できる | ディストリビューションの保守コストがかかる |
| ③ 新しいカーネル | Rust などで、ケイパビリティ型のカーネルから作る | 理想的な抽象を一から作れる | ドライバもアプリもない。数年単位の作業になる。GPUドライバがなく、AIの計算基盤も使えない |

**推奨**: ①のコアを OS に依存しない形で設計し、②で統合と実証を行う。③は不要。Linux の LSM / eBPF / Landlock で、必要な機能の大半は実現できる。

### ターゲットの候補（易しい順）
1. **ヘッドレスなエージェント実行環境**（クラウド、CI、サーバー）: GUI が不要で、需要が大きい。E2B や Firecracker 系のサンドボックスと競合する
2. **開発者向けワークステーション**: コーディングエージェントの利用者。最も早く採用が見込める
3. **一般ユーザー向けのデスクトップ／モバイル**: GUI、ドライバ、アプリのエコシステムが必要で、最も難しい

### ライセンス
- ユーザーランド: **Apache-2.0** を推奨（特許条項があり、標準として採用されやすい。MCP 関連のエコシステムとも合う）
- Linux カーネルモジュール、または GPL 限定のヘルパーを使う eBPF プログラム: GPL-2.0 が必須
- 上記2つはリポジトリを分けて管理するのが望ましい

## 7. 次に決めること

1. **ターゲット**: ヘッドレス／開発者ワークステーション／一般ユーザーのどれか
2. **実装アプローチ**: ①実行基盤／②ディストロ／①から②への段階的移行
3. **重点レイヤー**: B（エージェント実行基盤）を中心にするか、A（推論基盤）も最初から含めるか
4. **最初に作る垂直スライス（MVP）の候補**: 「1つのタスクを、CoWワークスペースで隔離して実行し、型付きのアクション経由で操作させ、監査ログを残し、差分をレビューしてからコミットする」
