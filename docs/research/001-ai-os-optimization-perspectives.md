## 0. サマリー

**既存OSの前提**：人間が直接操作し、作者の意図どおりに動く決定的なプログラムを実行する。

**AI時代のワークロード**：確率的に動き、間違えることも騙されることもある自律的な主体が、人間の代わりに長時間動き、高価なアクセラレータとトークン（＝お金）を使う。

課題のほとんどは、この前提のズレから生まれています。

### 主な結論

1. **大手OSは2025〜2026年にそろってエージェント対応を進めた。ただし後付けである。**
   - Windows：MCPのネイティブ対応、Agent Workspace、Agent ID
   - Apple：App Intents、App Schemas、MCP ⚠️二次情報
   - Android：AppFunctions、UI automation

   いずれも既存アプリとの互換性を保ったまま上に載せる形のため、**権限モデルやプロセスモデルといった土台は変わっていません**。

2. **新OSが差別化できるのは、既存OSが後付けしにくい部分。**
   - (a) エージェントを前提にした権限管理と情報フロー制御
   - (b) すべての操作を取り消せる仕組み（可逆性、トランザクション）
   - (c) エージェントをOSの第一級オブジェクトとして扱う実行モデル
   - (d) 監査と説明責任

3. **Linuxには部品がそろっているが、まとめる層がない。**
   カーネルには namespaces、cgroups、Landlock、seccomp、eBPF、Btrfs/OverlayFS、accelサブシステムがあります。足りないのは、これらを「エージェントのための意味」でまとめるユーザーランドです。AndroidがLinuxカーネルの上に新しいユーザーランドを作ったのと同じ構図が、最も現実的な戦略候補です。

4. **OSSの「Agent OS」は、実態はアプリ層のフレームワークがほとんど。**
   権限、資源、ファイルシステムといったOSの層まで踏み込んだOSSはほとんどなく、空白地帯になっています。

## 1. 「AIに最適化」には3つの意味がある

| 視点 | 問い | 具体例 |
|---|---|---|
| **A. エージェントがOSを使う** | AIがOSやアプリを操作しやすいか | GUI操作とAPIの違い、CLI出力の構造化、データの意味づけ |
| **B. モデルがOS上で動く** | 推論を効率よく安全に動かせるか | GPU/NPUのスケジューリング、モデルの共有、KVキャッシュ |
| **C. 人間がAIと協働する** | 人間がAIを監督し、止め、信頼できるか | 承認UX、取り消し、可視化、監査 |

セキュリティ、プライバシー、エコシステムの3つは、A〜Cすべてにまたがる横断的な関心事です。

## 2. 既存OSの前提とAI時代の現実

| 項目 | 既存OSの前提 | AI時代の現実 |
|---|---|---|
| 操作する主体 | 人間（キーボード、マウス、タッチ） | エージェント（API、意図、自然言語） |
| プログラムの性質 | 決定的で、作者の意図どおりに動く | 確率的。誤るし、**読んだデータで乗っ取られる** |
| 信頼の境界 | **コード**（悪意あるプログラムを防ぐ） | **データ**（善意のプログラムが悪意ある入力で操られる） |
| 権限の単位 | ユーザー、アプリ（一度許可すれば永続） | タスク、委任（期限付きで最小限、縮小方向のみ委任） |
| 実行時間 | ミリ秒〜秒。CPU処理が中心 | 分〜日。LLMの応答待ちが中心 |
| 主な資源 | CPU、RAM、ディスク | GPU/NPU、VRAM、KVキャッシュ、**トークン予算（お金）** |
| データの整理 | 人間が付けたパスと名前の階層 | 意味、関係、出所、信頼度 |
| 失敗したとき | 人間が気づいて直す | 高速かつ大量に誤る。**取り消せることが必須** |
| 出力 | 人間向けのテキストやピクセル | 構造化データと、コンテキスト予算に収まる要約 |

**最も本質的なズレは、信頼の境界がコードからデータに移ったことです。**
従来のセキュリティは「悪意のあるプログラムを実行させない」ことが中心でした。エージェントの脅威は「善意のプログラム（エージェント）が、読み込んだWebページやメールに仕込まれた指示（プロンプトインジェクション）で乗っ取られる」ことです。これは古典的な「混乱した代理人（confused deputy）」問題が大規模化したものです。このため、データの出所や流れを追う**情報フロー制御**がOSの役割として重要になります（→ 3.7）。

## 3. 観点ごとの詳細

### 3.1 操作インターフェース：GUIから「意味のある機能公開」へ【視点A】

**既存OSの問題**
- エージェントは「スクリーンショットを撮る → 推論する → 座標をクリックする」ループでアプリを操作しています（Computer Use）。ステップごとに画像を入力して推論するので遅く、トークン代がかさみ、UIが変わると壊れます。
  - 精度は急速に上がっています。OSWorld-Verified では人間のベースライン（約72%）を超えるスコアが報告されています ⚠️集計サイトの数値で未確認。それでも速度、コスト、安全性、アプリ側に拒否されるという問題は残ります。
- アクセシビリティツリー（macOS AX API、Windows UIA、Linux AT-SPI、Android AccessibilityService）が事実上のエージェント用APIになっています。しかし品質はアプリごとにばらばらで、「その操作が何を意味するか」は表現されません。
- アプリ側は、GUIの自動操作を不正なbotと区別できず、ブロックしてしまいます。
  - 2025年末、中国ByteDanceの「豆包（Doubao）」スマホアシスタントは、多数のアプリから操作を拒否されました。第2世代では、GUIの読み取りとクリックの模倣をやめ、MCPやA2Aといったプロトコルで連携する方式に転換したと報じられています。
- Linux（Wayland）は、セキュリティ上の理由で他アプリへの入力注入や画面取得を原則禁止しています。xdg-desktop-portal（RemoteDesktop、ScreenCast）を経由する必要があり、エージェントによる利用は想定されていません。

**各OSの現状**
- **Apple**：App Intents で、アプリの動作やエンティティを型付きで公開できます。WWDC26 では次の内容が報じられています ⚠️二次情報。
  - SiriKit の非推奨化と App Intents への一本化
  - App Schemas（アプリのデータと操作を意味のあるスキーマで記述する仕組み）
  - iOS 27 / macOS 27 でのシステム全体のMCP対応
- **Windows**：Ignite 2025 で次の機能が発表されました。
  - MCPのネイティブ対応
  - 端末上のエージェントコネクタ・レジストリ
  - File Explorer などの組み込みコネクタ
  - 研究段階では、Microsoft の UFO² が UIA、ネイティブAPI、画像認識を組み合わせた方式をとっています。
- **Android**：2026年2月に次の2つが発表され、どちらも Android 17 で拡張される予定です。
  - AppFunctions：Android 16 以降、アプリが関数を端末上のエージェントに公開できる
  - UI automation：専用の連携がないアプリをGeminiが操作する。ユーザーは進捗を見ていつでも引き継げ、購入前には警告が出る
- **Linux**：統一された仕組みはありません。D-Bus と AT-SPI が断片的に存在するだけです。

**最適化の方向性**
- **機能を第一の契約とするアプリモデル（Capability-first）**：アプリは「型付きのアクション、エンティティ、イベント」を宣言することを第一の契約とし、GUIはその表現方法の一つにすぎない、という設計にする。
- UIの状態を、**安定したIDを持つ構造化データとして差分で配信する**。スクリーンショットを不要にするのが目標。
- フォールバックとして、高品質なアクセシビリティ層と画像認識を組み合わせる。
- アプリ側が「エージェント経由の操作」を識別して許可できるようにする（誰の代理で、どの権限で操作しているか）。これにより、GUI操作がbot扱いされる問題を解消する。

### 3.2 コマンド、出力、エラーを機械が読める形に（Agent-Computer Interface）【視点A】

**既存OSの問題**
- Unix系ツールの出力は人間向けのテキストです。エージェントはそれをパースするため、ロケールやバージョンの違いで壊れます。
- 対話型の入力（y/n の確認、ページャ、エディタの起動、TUI）でエージェントが止まります。
- 巨大な出力がコンテキストウィンドウを埋めてしまいます。ビルドログの大半はノイズです。
- エラーメッセージの形式がばらばらで、次に何をすべきかを機械的に判断できません。
- man や `--help` などのドキュメントが構造化されていません。

**現状**
- PowerShell（オブジェクトをパイプラインで渡す）、Nushell（構造化データを扱うシェル）、一部ツールの `--json` オプション、AGENTS.md（リポジトリ単位のエージェント向け指示）。
- SWE-agent の研究では、LM向けに設計したインターフェース（ACI）にするだけで、エージェントの性能が大きく変わることが示されています。

**最適化の方向性**
- すべてのシステムコマンドで、**構造化出力（JSONなど）とそのスキーマ**を標準にする。
- **非対話モードを保証する**。TTYがなければ対話を求めないことを規約にする。
- エラーは「コード、原因、推奨される回復手順」を構造化して返す。
- 出力の要約、ページング、切り詰めをOS側で提供する（コンテキスト予算を意識した設計）。
- コマンドが自分の説明と引数を機械可読な形で記述し、MCPのツール定義などに自動変換できるようにする。

### 3.3 ツールやエージェントをつなぐプロトコルと、機能の登録簿【視点A】

**既存OSの問題**
- MCPサーバの設定は、エージェントアプリがそれぞれ別のJSONファイルで持っています。OSとして、どんな機能が提供されているかを把握できません。
- ローカルのMCPサーバは通常ユーザー権限で動き、認可も監査もありません。
- 機能の発見、バージョン管理、信頼（誰が作ったか）の仕組みが整っていません。

**現状**
- **MCP**：Linux Foundation 傘下の Agentic AI Foundation（AAIF、2025年12月設立）に移管されました。2026-07-28 版の仕様では、ステートレス化や Enterprise-Managed Authorization 拡張などが入ったと報じられています ⚠️二次情報。2026年8月のロードマップでは、**エージェントID**が最優先課題の一つです。
- **その他の標準**：A2A（エージェント同士の連携）、AGENTS.md、Agent Skills、WebMCP（W3C Community Group のドラフト）。
- **Windows**：MCPプロキシ層を置き、認証、認可、監査を一か所でまとめる設計です。

**最適化の方向性**
- **OS標準の機能レジストリとブローカー**：すべてのツール呼び出しをOSのブローカー経由にし、ポリシー評価、監査、レート制限をかける。
- 特定のプロトコルに依存しすぎない。MCPを第一級としつつ、A2Aなどへのアダプタ層を持つ。
- ツールの署名と出所を検証する。

### 3.4 実行モデル：エージェントをOSの第一級オブジェクトにする【視点B】

**既存OSの問題**
- OSの基本単位はプロセスとスレッドで、「目的、所有者、予算、権限、期限を持つタスク」という概念がありません。
- エージェントは時間の大半をLLMの応答待ちに使い、数分から数日動き続けます。再起動やスリープで状態が失われます。
- iOS と Android はバッテリー保護のためバックグラウンド実行を強く制限しており、長時間動くエージェントは終了させられます。
- 複数のエージェントが同じファイルやリソースを同時に変更したときに、調停する仕組みがありません。
- ファイル変更、メール着信、時刻、通知といったイベントで処理を起動する仕組みが、OSごとにばらばらです。

**現状（研究）**
- **AIOS**（Rutgers大学、arXiv 2403.16971）：「エージェントOSカーネル」をユーザーランドで実装しています。具体的には、LLM用のシステムコール、エージェントのスケジューラ、LLMコンテキストの退避と復元（スナップショット/リストア）、メモリ・ストレージ・ツール・アクセスの各マネージャを持ちます。
- **MemGPT / Letta**：コンテキストウィンドウを仮想メモリのように階層管理します。

**最適化の方向性**
- **Agent/Task オブジェクト**を導入する。ID、親子関係（委任ツリー）、目標、権限、予算（トークン、金額、時間）、状態、期限を持たせる。
- **永続実行（durable execution）**：チェックポイントから再開でき、再起動をまたいで処理を続けられるようにする。
- リソースに**リースやロック**をかけ、エージェント同士の競合を検出する。
- **統一されたイベントバス**を用意する（時刻、ファイル、通知、外部Webhook、意味的な条件）。
- 対話中のタスクとバックグラウンドのタスクを区別してスケジューリングする。

### 3.5 計算資源の管理：GPU/NPU、メモリ、電力【視点B】

**既存OSの問題**
- OSのスケジューラとメモリ管理はCPUとRAMが中心です。GPUやNPUはベンダーのドライバとユーザーランドのランタイムに任されていて、OSからは見えにくくなっています。公平な共有、プリエンプション（実行中の処理の割り込み）、優先度の制御が弱い状態です。
- アプリがそれぞれ自前でモデルを同梱するため、GB単位の似たような重みがディスクとメモリに重複します。
- 推論の作業メモリであるKVキャッシュの管理は、推論エンジン任せです。vLLM の PagedAttention は、OSの仮想メモリのページングをKVキャッシュに応用した例で、**OSの知見がそのまま効く領域**です。
- ノートPCやスマホで推論を続けると、電力と熱の制約が大きくなります。
- Apple Silicon や AMD Strix Halo などのユニファイドメモリでは、CPUメモリとGPUメモリの区別があいまいになっています。

**現状**
- **OSレベルの共有モデルサービス**
  - Apple：Foundation Models framework
  - Android：AICore（Gemini Nano）
  - Microsoft：Foundry Local（同じモデルは1回だけダウンロードする設計）、Windows ML
  - Ubuntu：inference snaps（シリコンに合わせて推論エンジンと量子化を自動選択）
- **Linuxカーネル**
  - `drivers/accel`：NPUなどのアクセラレータ用サブシステム（6.2以降）
  - dmem cgroup：デバイスメモリの制御（6.14以降）
- **研究**：OS的な発想をとり入れた推論基盤の研究が増えています。
  - kvcached：KVキャッシュに仮想メモリの方式を適用し、複数のモデルで1つのGPUを共有する
  - Valve：オンライン推論とオフライン推論を同じGPUで動かし、KVキャッシュを回収する

**最適化の方向性**
- **推論をOSのサービスにする**（音声におけるPipeWireのようなもの）。モデルの重みを共有（mmap、重複排除）し、要求を優先度付きでスケジューリングし、プリエンプションできるようにする。
- **KVキャッシュやプロンプトキャッシュを、OSが管理するメモリ階層として扱う**。エージェント間で共通の接頭辞を共有し、VRAM → RAM → SSD の階層に置く。
- ローカルとクラウドのどちらで推論するかを、プライバシー、コスト、レイテンシ、電力のポリシーで決める。
- 電力と熱を考慮して推論をスケジューリングする（重いバックグラウンド処理は充電中に回す、など）。

### 3.6 モデルのライフサイクル管理【視点B】

**既存OSの問題**
- モデルは共有ライブラリのように扱われるべきなのに、バージョン管理、署名、ライセンス、能力の記述が標準化されていません。
- pickle形式による任意コード実行など、サプライチェーン攻撃を受ける余地があります。
- モデルを更新すると挙動が変わり、エージェントの再現性が崩れます。

**最適化の方向性**
- モデルをパッケージとして管理する。署名を検証し、出所とライセンスのメタデータを持たせ、safetensors などの安全な形式を必須にする。
- バージョンを固定（pinning）でき、A/B更新とロールバックができるようにする。
- 能力の記述（コンテキスト長、対応モダリティ、ツール呼び出しの可否、評価結果）をもとに、どのモデルに振るかを決める。

### 3.7 権限とセキュリティモデル【横断：最重要】

**既存OSの問題**
- **アンビエント権限**：ユーザーとして動くプロセスは、そのユーザーの全ファイルと全認証情報にアクセスできます。エージェントをユーザー権限で動かすと、被害の範囲はユーザーの全資産になります。
- **プロンプトインジェクション**：LLMは、読み込んだデータ（Webページ、メール、ファイル）に含まれる指示に従ってしまいます。モデル側だけでは確実に防げないことが、研究で繰り返し示されています。
- 既存の権限は、アプリ単位、リソース単位で、一度許可すれば永続します。「このタスクの間だけ許可する」「このデータはこの宛先に送ってはならない」といったことを表現できません。
- 確認ダイアログを出しすぎると承認疲れが起き、確認が形だけになります。

**設計の指針になる考え方**
- **致命的な三要素（lethal trifecta、Simon Willison）**：「私的データへのアクセス」「信頼できないコンテンツへの露出」「外部への通信」の3つがそろうと、データが流出しうる。
- **Agents Rule of Two（Meta、2025年10月）**：1つのセッションで次の3つのうち2つまでしか持たせない。
  - (1) 信頼できない入力を処理する
  - (2) 機密システムや私的データにアクセスする
  - (3) 状態を変更する、または外部と通信する
- **CaMeL（Google DeepMind）**：信頼できるユーザーの指示から制御フローを取り出し、信頼できないデータが制御フローを変えられないようにする。値に「出所」と「読んでよい相手」というケイパビリティを付ける。
- **FIDES（Microsoft）**：エージェントが扱うデータに機密性と完全性のラベルを付けて動的に追跡（テイント追跡）し、ポリシーに反するデータの流れを決定的にブロックする。

**これらはどれもアプリやフレームワークの層で実装されており、OSが強制する仕組みにはなっていません**（今回の調査範囲では見つかりませんでした）。ここが新OSにとって最大の機会です。

**現状**
- **Windows**：エージェントは専用のIDを持ち、分離された Agent Workspace で動きます。デフォルトは最小権限で、明示的に許可されたリソースにしかアクセスできません。
- **サンドボックス技術**：Linux（namespaces、seccomp、Landlock、bubblewrap）、macOS（Seatbelt、Apple Containerization）、microVM（Firecracker、Kata）、gVisor。コーディングエージェントの各社は、これらを独自に組み合わせています。Landlock を使った研究段階のサンドボックス（Sandlock など）も出てきています。

**最適化の方向性（新OSの中核候補）**
- **ケイパビリティベースのセキュリティ**：権限は「タスク単位で、期限付きで、必要最小限を」与える。委任するときは縮小する方向にしかできない。先行例は Fuchsia や seL4。
- **OSレベルの情報フロー制御（IFC）**：データに出所と機密性のラベルを付け、データの流れをOSが強制する。たとえば「信頼できない入力に触れたタスクは、承認なしに外部へ送信できない」というルールを、カーネルやブローカーで強制する。これは **Rule of Two をシステムの仕組みにしたもの**です。
- **計画役と実行役の分離**：CaMeL のような「2つのLLMに役割を分けるパターン」を、OSの標準的な実行形態として提供する。
- **デフォルトでサンドボックス**：エージェントのタスクはすべて隔離環境で始め、必要に応じて権限を上げる。
- **リスクの段階に応じた承認**：取り消せる低リスクの操作は自動で通し、取り消せない高リスクの操作は人間が承認する。承認は個々の操作ではなく計画単位でまとめて行う。
- 組織やユーザーが、宣言的なポリシー言語（Cedar、OPA/Rego など）でルールを書けるようにする。

---

### 3.8 アイデンティティ、認証情報、委任【横断】

**既存OSの問題**
- エージェントはユーザーと同じcookie、キーチェーン、トークンを使うため、人間の操作とエージェントの操作を区別できません。
- APIキーなどの秘密情報が、環境変数やファイルとしてエージェントのコンテキストに入り、流出する危険があります。
- パスキーや2FAは、人間がその場にいることを前提にしています。
- 「ユーザー → エージェント → サブエージェント」と委任が連鎖したときに、権限を絞り込んだり追跡したりする仕組みがありません。

**現状**
- Windows の Agent ID。
- MCP 2026-07-28 版の Enterprise-Managed Authorization 拡張と、client credentials 拡張 ⚠️二次情報。
- IETF WIMSE ワーキンググループでの、AIエージェント認証のドラフト（draft-ietf-wimse-aims）。
- Web上でbotやエージェントを識別する **Web Bot Auth**（IETFのワーキンググループ。HTTP Message Signatures を使う）。

**最適化の方向性**
- エージェントごとのIDを持たせる（ワークロードID。SPIFFE などの考え方）。委任の連鎖は、**権限を絞り込めるトークン**（OAuth Token Exchange、Macaroons、Biscuit など）で表す。
- **シークレットブローカー**：エージェントには秘密情報そのものを見せない。OSがネットワークの境界（プロキシ）で認証情報を差し込む。
- 「この操作はエージェントによるもの」ということを、OSが外部サービスに暗号学的に示す（Web Bot Auth などをOSが代行する）。

---

### 3.9 取り消せること（可逆性）とトランザクション【視点C】

**既存OSの問題**
- 「元に戻す」はアプリごとの機能で、OS全体での取り消しはありません。ファイル操作はトランザクションになっていません。
- エージェントは誤ることを前提に設計すべきですが、誤った操作（rm、設定変更、パッケージの導入）を巻き戻すのは困難です。
- メール送信、決済、外部APIの呼び出しといった外部への副作用は、原理的に巻き戻せません。

**現状**
- ファイルシステムのスナップショット（APFS、Btrfs、ZFS）、Time Machine や Windows のシステムの復元（粒度が粗い）、Replit などのサービス側のチェックポイント。
- **DeltaBox**（arXiv 2605.22781）：OverlayFS、CRIU、コピーオンライトを組み合わせ、ファイルシステムとプロセスの状態をミリ秒単位でチェックポイント、ロールバックします。
- 送信や決済などの取り消せない操作をアウトボックスに保留する、小規模なOSSツールも出てきています。

**最適化の方向性**
- **タスクごとのコピーオンライト作業領域**：エージェントの変更をまず上書き層に書き、差分をレビューしてから確定（コミット）する。gitのステージングと同じ発想です。
- **操作を可逆性で分類する**：
  - 可逆：スナップショットで戻せる
  - 補償可能：取り消し用のAPIがある
  - 不可逆：送信や決済
  - 不可逆な操作は**アウトボックス**に保留し、承認されてから実行する。
- 実行計画を事前に示す **dry-run** を、システムAPIの標準機能にする。
- CRIU などで、プロセスの状態まで含めてチェックポイントをとる。

---

### 3.10 監査、可観測性、説明責任【視点C】

**既存OSの問題**
- 既存のログは管理者向けです。「どのエージェントが、誰の代理で、どの入力を根拠に、どの権限で、何をしたか」を追えません。
- トークン消費やAPI料金を、エージェント単位で集計する仕組みがありません。

**最適化の方向性**
- **改ざんを検知できる監査ログ**（追記専用、署名付き、ハッシュチェーン）。
- **因果関係のグラフ**：「入力（どのWebページやメールを読んだか）→ 判断 → 操作」をつないで記録し、事故が起きたときに、どの注入が原因かをさかのぼれるようにする。
- **リプレイ**：記録から再実行して検証できるようにする。
- **エージェント単位の資源の集計**（トークン、金額、GPU時間）と、上限の設定（Unix の rlimit に相当）。
- 標準形式を使う：OpenTelemetry の GenAI セマンティック規約、AI生成コンテンツの出所表示には C2PA。

---

### 3.11 データ、ファイルシステム、作業の文脈【視点A】

**既存OSの問題**
- ファイルは人間が付けたパスと名前で整理されていて、意味、関係、出所を表すメタデータが乏しい状態です。
- 検索はキーワード中心です。AIアプリはそれぞれ独自にインデックス（埋め込み）を作るので、重複が生じ、元ファイルのアクセス権が反映されないこともあります。
- 「ユーザーがいま何をしているか」という文脈を得る手段が、スクリーンショットしかありません。画面を常時記録する Windows Recall は、プライバシー面で強く批判され、設計の見直しを迫られました。
- ファイル形式がアプリ固有で、中身をAIが扱える形に取り出すのが困難です。

**最適化の方向性**
- **OS標準のセマンティックインデックス**（全文検索、ベクトル、知識グラフ）。**元データのアクセス権を引き継いだ**検索にし、権限のないエージェントには結果が見えないようにする。
- PDF、Office文書、画像などを構造化テキストに変換する**共通のコンテンツ抽出**をOSサービスとして提供する。
- データの**出所ラベル**（ユーザーが作成、外部から取得、AIが生成）を拡張属性として持たせ、情報フロー制御（3.7）と連携させる。
- 生のスクリーンショットの代わりに、**構造化された操作履歴**を、ユーザーの管理下で提供する。

---

### 3.12 記憶とパーソナルな文脈【視点A/C】

**既存OSの問題**
- ChatGPT、Claude、Gemini、Copilot などがそれぞれ別々にユーザーの記憶を持っています。乗り換えられず、まとめて確認したり削除したりもできません。
- 記憶に悪意ある内容を書き込まれる（memory poisoning）危険があります。

**最適化の方向性**
- **ユーザーが所有する記憶ストア**をOSのサービスにする。範囲（エージェント別、プロジェクト別、共有）、閲覧・編集・削除のUI、エクスポート、保持期間を持たせる。
- 記憶ごとに出所を記録し、信頼できない入力から来た記憶を区別する。
- どのエージェントがどの記憶を読んだかを監査できるようにする。
- OSSのOSにとって、「ユーザーがデータと記憶を所有する」ことは、大手プラットフォームに対する最もわかりやすい差別化軸になります。

---

### 3.13 プライバシーとローカルファースト【横断】

**既存OSの問題**
- 高性能なモデルの多くはクラウドにあり、個人のデータが外部に送られます。どのデータがどこに送られたかを、ユーザーは把握できません。

**現状**
- Apple Private Cloud Compute（第三者が検証できるクラウド推論）と、各社の端末上で動くモデル。

**最適化の方向性**
- **ローカル処理を優先**し、クラウドを使うときは**データ送信ポリシー**（何を、どのプロバイダに、どんな条件で送るか）をOSが強制し、見える化する。
- 送信する前に機密情報を検出し、マスキングする。
- クラウド推論の検証には、機密計算（TEE、リモートアテステーション）を前提にする。

---

### 3.14 人間とAIの協働UX【視点C】

**既存OSの問題**
- 入力フォーカスとカーソルが1つしかないので、エージェントがGUIを操作している間、ユーザーは作業できません。
- バックグラウンドのエージェントが何をしているかが見えません。
- 途中で介入したり、作業を引き取ったり返したり（take over / hand back）する標準的な方法がありません。
- 確認ダイアログが乱発されます。

**現状**
- Windows の Agent Workspace（エージェント専用の分離されたデスクトップ）。
- UFO² の Picture-in-Picture（仮想デスクトップでエージェントと人間が並行して作業する）。
- Android と Gemini の UI automation（進捗を見ていつでも引き継げ、購入前に警告が出る）。

**最適化の方向性**
- **エージェント専用の仮想ディスプレイまたはセッション**（画面なしでも動ける）。
- **アクティビティセンター**：すべてのエージェントの計画、進捗、権限、コストを一覧し、一時停止、中止、引き継ぎができる。
- 計画をプレビューして、まとめて承認できるようにする（3.7 のリスク段階と連動）。
- 自然言語と構造化UIを組み合わせたシェルにし、音声などのマルチモーダル入力を第一級に扱う。

---

### 3.15 ネットワーク、Web、外部サービス【視点A】

**既存OSの問題**
- Webは人間向けに作られており、CAPTCHAやbot検知がエージェントを阻みます。
- エージェントの外部通信を宛先ごとに制御する仕組みが一般的ではありません。外部通信はデータの流出経路になります。

**現状**
- **WebMCP**：WebサイトがエージェントにツールをJSで登録する仕組み。W3C Community Group のドラフトで、Chrome のフラグ付きプレビューの段階です。
- **Web Bot Auth**（IETF）。
- **llms.txt**。
- エージェントによる決済のプロトコル（AP2 など）。

**最適化の方向性**
- **エージェントごとの外部通信（egress）ポリシー**：許可する宛先ドメイン、データ量、通信内容のラベル検査。
- スクレイピングより、WebMCP や API などの構造化されたインターフェースを優先するネットワークスタックにする。
- 決済などの高リスクな操作には、専用の承認と上限を設ける。

---

### 3.16 ソフトウェア環境と再現性【視点A】

**既存OSの問題**
- エージェントはパッケージを入れたり設定を書き換えたりして、環境を汚します。
- LLMが存在しないパッケージ名をでっち上げ、攻撃者がその名前を先回りして登録する「スロップスクワッティング」が報告されています。
- システムの状態がグローバルに書き換え可能なので、再現やロールバックが困難です。

**最適化の方向性**
- ベースOSを書き換え不可能にし（ostree / Fedora Atomic、NixOS など）、**タスクごとに使い捨ての環境**を用意する。
- 環境を宣言的に定義し（Nix や Guix の考え方）、エージェントが作った環境を再現できるようにする。
- パッケージの出所を検証し、新しいパッケージや評価の低いパッケージを入れるときは追加の確認を挟む。

## 7. 決める必要がある戦略上の論点

> **2026-11-08 更新**：Linux カーネルの上に新しいユーザーランドを作る方針（7.1 の (b)）に決めました。ユーザーランドは1つにし、人間はすべての作業をエージェントへの依頼で行います。ファイル管理の検討は [#002](002-file-management.md)、図解は [docs/diagrams/index.html](../diagrams/index.html) にあります。

### 7.1 どの層を作るか
| 選択肢 | 長所 | 短所 |
|---|---|---|
| (a) カーネルから新規に作る | 設計の自由度が最大 | GPU/NPUなどのドライバの壁。実用化まで10年単位 |
| **(b) Linuxカーネルの上に新しいユーザーランドを作る（Android型）** | ドライバと既存のプリミティブを使える。差別化点はほぼユーザーランドで実現できる | Linux既存アプリとの互換性をどう扱うかを決める必要がある |
| (c) 既存OSの上に載るミドルウェア/ランタイム | 導入しやすく、すぐ使ってもらえる | ホストOSの権限モデルに縛られ、強制力に限界がある |

**推奨は (b) を本体にすることです。** あわせて、ブローカー、ポリシー、監査、記憶などのコアは (c) としても動くように移植性を持たせます。理由は次のとおりです。
- §6 の★★★の観点は、ほぼ Linux のプリミティブとユーザーランドで実装できます。
- (c) で既存OSのユーザーにも使ってもらえれば、OSSとしての普及経路を確保できます。

### 7.2 最初に狙う環境
- 候補：画面なし（サーバ、VM、開発環境でのエージェント実行基盤）／デスクトップ／モバイル／組み込みやロボット。
- **推奨は、最初は画面なしのCLI中心にすることです。**
  - GUIアプリの互換性という最難関を避けられます。
  - コーディングエージェントや業務自動化といった、明確な利用者がいます。
  - デスクトップは第2段階にします。

### 7.3 その他
- **既存アプリとの互換性の範囲**：Linuxアプリをそのまま動かすか、サンドボックス内に限定するか。
- **モデルへの中立性**：ローカルモデルと任意のクラウドAPIを同列に扱い、特定のベンダーに依存しない。
- **ライセンス**：カーネルは GPL-2.0 のまま。ユーザーランドは、特許条項があり企業が採用しやすい Apache-2.0 が有力（AOSP や Kubernetes と同じ）。
- **脅威モデル**：何を何から守るのか（プロンプトインジェクション、悪意あるツールやMCPサーバ、モデルの誤作動、サプライチェーン、物理アクセス）。
- **ガバナンス**：意思決定の方法、脆弱性の開示ポリシー、標準化団体（AAIF など）との関わり方。

## 8. 次のステップ案

1. §7 の論点を決める（特に、どの層を作るかと、最初に狙う環境）。
2. **脅威モデルの文書**を書く（`docs/threat-model.md`）。セキュリティが中核なので、これがすべての設計の出発点になります。
3. **アーキテクチャ案**を書く（`docs/architecture.md`）。Agent/Task オブジェクト、ブローカー、ポリシーエンジン、作業領域、監査ログの関係を整理します。
4. **PoC 候補**：Linux 上で「エージェント用タスクランタイム」を最小限に実装する。
   - タスク単位のサンドボックス（namespaces、Landlock、seccomp）
   - OverlayFS / Btrfs による作業領域と、差分を見てからのコミット
   - MCPブローカー（ポリシー評価と監査ログ）
   - egressプロキシ（宛先の制限とシークレットの差し込み）
