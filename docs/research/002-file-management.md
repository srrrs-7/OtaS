## 前提（2026-11-08 の決定）

- **ユーザーランドは1つにする。** 従来型のデスクトップ環境や、互換用のユーザーランドを並べて持たない。
- **人間はすべての作業をエージェントに依頼する。** OSが処理する単位は、エージェントのタスク。
- **カーネルは Linux を使う**（2026-11-08 決定）。ユーザーランドの実装言語は Rust を検討中。

---

## 結論

**層に分けて判断します。**

**残すもの**：「ファイル」という形式と、「パス」という住所。

**作り直すもの**：次の4つです。
- 誰に何が見えるか
- 変更をどう確定するか
- データにどんな意味と出所があるか
- 人間がどうデータに触れるか

| 層 | 判断 | 理由 |
|---|---|---|
| 保存層（ブロック管理・ジャーナル） | **踏襲**（Btrfs） | 成熟している。スナップショットとコピーオンライトが「取り消し」の土台になる |
| ファイルAPIと階層パス（POSIX） | **踏襲**（見え方はタスクごとに組み立てる） | 既存ツールが動く。LLMが最も扱い慣れた形式 |
| 権限（ユーザー単位の rwx / ACL） | **置き換え** | タスク単位の名前空間とラベルにする |
| 意味・出所・履歴 | **新設** | 安定ID、ラベル、索引、版管理 |
| 人間がフォルダを作って整理する操作 | **廃止** | エージェントに頼む方式と、問い合わせで作るビューに置き換える |

---

## 1. 踏襲する理由：ファイルはすでにAIに向いた形式である

- **LLMにとって「母語」である。**
  - LLMは学習データの中で、Unixのファイル操作（`ls`、`cat`、`grep`、パス）を大量に見ています。
  - コーディングエージェントが実用レベルに達したのは、ファイルとシェルという環境で動けたことが大きい要因です。
- **エージェント開発の現場で、ファイルが外部記憶の定番になっている。**
  - Manus は、ファイルシステムを「サイズ無制限で永続し、エージェントが直接操作できる究極のコンテキスト」と位置づけています。`todo.md` を更新し続けることで、長いタスクでも目標を見失わないようにしています。
  - Agent Skills はファイルのフォルダです。AGENTS.md もファイルで、Claude Code の記憶も Markdown ファイルです。
- **既存のツールがPOSIXを前提にしている。** コンパイラ、Python、git、各種CLIを「エージェントの道具」として動かすには、POSIXのファイルAPIが必要です。
- **人間が中身を確かめられる。** テキストのファイルは人間が読んで検証できます。データベースの中身はブラックボックスになりがちです。
- **過去の失敗に学べる。**
  - Microsoft の WinFS は、リレーショナルDBをファイル管理の中心に置こうとしましたが、2006年に中止されました。
  - iOS はファイルを隠しましたが、データがアプリごとに閉じ込められ、iOS 11（2017年）で「ファイル」アプリを追加することになりました。

---

## 2. 既存のファイル管理のままでは困る点

| 既存の性質 | エージェント時代の問題 | 対応する層 |
|---|---|---|
| 権限がユーザー単位 | タスクが必要以上の権限を持つ（#001 3.7） | タスク単位の視界と権限 |
| 書き込むと即座に上書きされる | 取り消せない。並行して動くタスク同士がぶつかる | 上書き層とコミット |
| 出所や信頼度のメタデータがない | 情報フロー制御ができない | 意味層（ラベル） |
| ファイルは1か所にしか置けず、名前は人が付ける | 意味で探せない | 意味層（索引） |
| 識別子がパス | 移動や改名で、記憶や監査ログからの参照が切れる | 意味層（安定ID） |
| メール・予定・連絡先がアプリ固有のDBに閉じている | エージェントがデータを横断して扱えない | オープンな形式のファイルにそろえる |

---

## 3. 提案：4層の構成

### 3.1 保存層（踏襲）：Btrfs

- コピーオンライトのスナップショット、サブボリューム、reflink（実データを共有するコピー）、チェックサムを備えています。
- カーネル本体（メインライン）に含まれています。
- ZFS は高機能ですが、ライセンス（CDDL）が GPL と両立しないため、カーネル本体に入っていません。OSSの標準構成には向きません。

### 3.2 ファイルAPIと階層パス（踏襲。見え方は変える）

- **タスクごとの名前空間**を使います。考え方は Plan 9 の「プロセスごとの名前空間」と同じです。
  - タスクには、許可された部分だけを組み立てたツリーを見せます（mount namespace、bind mount、OverlayFS）。
  - 許可されていないパスは、タスクの中には存在しません。
  - Landlock で、アクセスの種類（読み取りのみ、など）をさらに絞ります。
- **パスは「住所」から「そのタスクの視界」に変わります。** パスの見え方そのものが権限の仕組みになります。
- エージェントも既存ツールも、普通のファイルとして読み書きするだけで済みます。特別なAPIは要りません。

### 3.3 意味層（新設）

| 要素 | 内容 |
|---|---|
| 安定ID | パスとは別の識別子をファイルに付ける。一般のプロセスが書き換えられない拡張属性（`trusted.*` など）に保存する。記憶、監査ログ、ファイル間のリンクはIDで参照する |
| ラベル | 出所（ユーザーが作成、外部から取得、AIが生成、どのタスクか）、機密度、信頼度。保護された拡張属性に保存し、BPF LSM でポリシーを強制する |
| ラベルの伝播 | タスクが書いたファイルには、そのタスクが読んだもののラベルを自動で付ける。Flume や HiStar の「分散情報フロー制御（DIFC）」を、タスク単位で適用する考え方。ツールがラベルを知らなくても、OSがタスク単位で強制できる |
| 索引 | 全文検索、ベクトル、関係グラフ。fanotify で変更を追う。ラベルとタスクの権限を守り、見えないものは検索結果にも出さない |
| 履歴 | コミットのたびにスナップショットを取るので、すべての変更が版として残る |

**原則：データの正本はファイル、DBは派生物にする。** 索引はいつでもファイルから作り直せるようにします。これがWinFSの失敗を避ける要点です。

### 3.4 人間のビュー（新設。フォルダ操作は廃止）

- 人間はフォルダを開いて探しません。エージェントに「先週の契約書」のように頼みます。
- 画面には、問い合わせから作る**仮想ビュー**（プロジェクト別、時系列、人物別、タスク別）を表示します。
  - 先行例：Semantic File System（1991年。問い合わせで仮想ディレクトリを作る）、Lifestreams（1996年。時系列のストリーム）、BeOS の属性検索。
- **レビュー受け箱**：エージェントが加えた変更の差分を確認し、承認する場所です。人間とファイルの主な接点はここになります。
- 人間が直接編集したい場合は、それも「人間のタスク」として同じコミット経路に乗せます。こうすれば、履歴、ラベル、衝突の扱いを1つの仕組みにまとめられます。

## 4. 書き込みと確定の流れ（図6）

1. タスクを始めるときに、`/data` の読み取り専用スナップショット（base）を作ります。Btrfs ならほぼ一瞬で作れます。
2. タスクの名前空間に OverlayFS を組みます。下層は base のうち許可された部分、上層はタスク専用の上書き層（upper）です。
   - 下層を固定のスナップショットにするのは、OverlayFS では、マウント中に下層を変更したときの動作が未定義とされているためです。
3. エージェントは普通にファイルを読み書きします。変更はすべて upper に入ります。
4. タスクが完了したら、upper の差分を提示します。人間またはポリシーがレビューします。
5. コミットするときは、base、upper、現在の `/data` の3つを比べます（git の3者マージと同じ考え方の、楽観的な並行性制御）。
   - 衝突がなければ、変更を適用し、新しいスナップショット（版）を作ります。
   - 衝突があれば、エージェントに解決させるか、人間に確認します。
6. 変更を破棄するときは、upper を消すだけです。コミット後に取り消したいときは、前の版のスナップショットに戻します。

メール送信や決済のような、取り消せない外部への操作はファイルではないので、アウトボックスで別に管理します（#001 3.9、図3）。

## 5. ディレクトリ構成案

```
/                ベースOS（読み取り専用、A/B更新）
/store/          内容アドレスで管理する不変のオブジェクト（モデル、パッケージ、実行環境）
                 Nix store と同じ考え方。同じものは1つだけ置く
/data/           ユーザーデータの正本（Btrfs サブボリューム。コミットごとにスナップショット）
  projects/
  documents/
  media/
  mail/          Maildir
  calendar/      iCalendar
  contacts/      vCard
  memory/        エージェントの記憶（Markdown）
/tasks/<id>/     タスクごとの作業領域（upper、計画、ログ）。コミットか破棄で片付ける
/audit/          追記専用の監査ログ
```

タスクから見えるツリーの例（図5）：

```
/work        ← /data/projects/a を OverlayFS で重ねたもの（読み書き可。変更は upper へ）
/in/mail     ← /data/mail の読み取り専用 bind mount（ラベル：私的）
/tools       ← /store の読み取り専用 bind mount
/tmp         ← タスク専用（空の状態から始まる）
```

メール、予定、連絡先も**オープンな形式のファイル**（Maildir、iCalendar、vCard）として `/data` に置きます。理由は3つです。
- エージェントがほかのデータと同じ方法で扱える。
- 同じラベルと権限の仕組みがそのまま効く。
- ユーザーがデータを持ち出せる。

## 6. 先行事例と教訓

| 事例 | 何をしたか | 教訓 |
|---|---|---|
| WinFS（Microsoft、2003〜2006年） | リレーショナルDBをファイル管理の中心に置いた | 複雑さ、性能、互換性の問題で中止された。DBは正本にせず、索引にとどめる |
| BeOS BFS | ファイルの属性に索引を付け、保存した問い合わせで検索できた | 意味で探す仕組みは、ファイルシステムの上に載せられる |
| iOS（2007年〜） | ファイルを隠し、データをアプリごとに閉じ込めた | データが孤立した。iOS 11 で「ファイル」アプリを追加 |
| Plan 9 | プロセスごとに名前空間を組み立てた | パスの見え方を、そのまま権限として使える |
| Nix store | 内容アドレスで管理する不変のストア | 再現性と重複排除に効く。モデルやパッケージなど変わらないもの向き |
| git | スナップショットと3者マージ | 並行作業と取り消しのモデルになる |
| Semantic File System（1991年）、Lifestreams（1996年） | 問い合わせで作る仮想ディレクトリ、時系列のストリーム | 人間向けビューの先行例 |
| Flume、HiStar | OSレベルの分散情報フロー制御 | ラベルをプロセス単位で追跡し、強制できる |

## 7. 未決定事項とリスク

- **複数人での利用**：家族やチームでの共有を想定するか。ラベルと名前空間の設計に影響します。
- **クラウドサービスとの同期**：Gmail や Google Drive のデータを、ローカルに実体として持つか、コネクタ経由でその都度取得するか。
- **大きなファイル**：動画やデータセットを OverlayFS で書き換えると、最初にファイル全体のコピー（コピーアップ）が起きます。Btrfs 上なら reflink を使ってコストを抑えられる見込みですが、検証が必要です。
- **ファイル内部の同時更新**：SQLite などは、ファイル単位の衝突として扱われます。
- **ラベルが広がりすぎる問題**：ラベルをタスク単位で付けると粒度が粗くなります。一度でも信頼できない入力を読んだタスクは、出力がすべてラベル付きになります。対策は次の2つです。
  - タスクを小さく分ける。
  - 人間の承認、または隔離した下位エージェント（CaMeL型）を通した場合に限り、ラベルを外せるようにする。
- **人間が直接触れる経路**：閲覧だけを許すか、編集も許すか。編集を許す場合は、「人間のタスク」として同じコミット経路に乗せる案があります。
