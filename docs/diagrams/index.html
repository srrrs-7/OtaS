図1全体の構成

処理の単位はエージェントのタスクです。タスクはそれぞれ別のサンドボックスで動き、外の世界に作用する手段はブローカーを通る呼び出ししかありません。

図2タスクの一生

タスクは「計画 → 実行 → レビュー → コミット」の順に進みます。危険度に応じて承認をはさみます。どの段階でも捨てられ、確定した後でも取り消せます。

図3ラベルによる情報フロー制御

プロンプトインジェクションをモデルだけで確実に防ぐことはできません。そこで、データの出所をラベルで追跡し、危険な組み合わせをOSが止めます。

図4ファイル管理：踏襲するものと作り直すもの

人間はすべての作業をエージェントに依頼するので、フォルダを人が整理する前提は不要になります。一方で、ファイルとパスはエージェントと既存ツールが最も扱い慣れた形式です。そこで、層ごとに判断を分けました。

結論：ファイルという形式とパスという住所は踏襲します。誰に何が見えるか、変更がどう確定するか、データにどんな意味と出所があるかを作り直します。

図5タスクから見えるファイル

タスクには、許可された部分だけを組み立てたファイルツリーを見せます。パスは「住所」から「そのタスクの視界」に変わり、見え方そのものが権限になります。

図6書き込みと確定

エージェントの書き込みは、正本にすぐには反映されません。タスク専用の上書き層にたまり、比較してから確定します。git のブランチとマージに近い動きを、ファイルシステムの層で行います。

付録ディレクトリ構成案

メール、予定、連絡先も、オープンな形式のファイルとして /data に置きます。エージェントがほかのデータと同じ方法で扱え、同じラベルと権限の仕組みが効き、ユーザーがデータを持ち出せるからです。

OS全体

/               ベースOS（読み取り専用、A/B更新）
/store/         内容アドレスで管理する不変のオブジェクト（モデル・パッケージ・実行環境）
/data/          ユーザーデータの正本（Btrfs サブボリューム、コミットごとにスナップショット）
  projects/
  documents/
  media/
  mail/         Maildir
  calendar/     iCalendar
  contacts/     vCard
  memory/       エージェントの記憶（Markdown）
/tasks/<id>/    タスクごとの作業領域（upper・計画・ログ）。コミットか破棄で片付ける
/audit/         追記専用の監査ログ

タスクAから見えるツリー（図5）

/work       ← /data/projects/a を OverlayFS で重ねたもの（読み書き可）
/in/mail    ← /data/mail の読み取り専用 bind mount（ラベル：私的）
/tools      ← /store の読み取り専用 bind mount
/tmp        ← タスク専用（空の状態から始まる）
